# 폼지 자동입력 (form auto-fill) 구현 계획

> 목표: 수기로 채우던 대수회 시험지 폼(.hwp)을 OCR 결과로 **자동 입력**.
> 폼 = 머리말/꼬리말·2단·문항번호(미주 자동번호)·보기 ①②③④⑤ 사전배치가 완성된 양식.
> 산출물 예시: `D:\기출\기출작업\*차\*(워드).hwp`

## 검증 완료 (프로토타입)
- 미주 앵커(`ctrl.GetAnchorPos`)로 문항번호 본문좌표 획득 → `SetPos` 이동 → 삽입.
- `RepeatFind`로 보기 ①~⑤ 마커 탐색 → 다음에 보기 내용 삽입(폼 2열 정렬 재사용).
- 슬롯 **삭제**: `SelectText(spara,spos,epara,epos)`+`Run("Delete")` → 미주 자동 재번호.
- 슬롯 **복사**: `SelectText`+`Run("Copy")`+`SetPos`+`Run("Paste")` → 미주 자동 재번호.

## 폼 구조 (중3 빨강 기준)
- 25 슬롯, 2 구역. 슬롯 1~17 객관식(①②③④⑤ + [중단원][난이도]), 18~25 서술형([서답형]·[조건]칸).
- 끝에 `정답 / 워드:t / 오검:t / 완료:t` 마커(답지 구분).
- 페이지당 문항 수는 **내용 높이로 자연 흐름**(하드 페이지나눔 아님). 빈 템플릿은 5/쪽, 채운 본은 6/쪽.

## 페이지 규칙 (사용자)
- 한 페이지 최대 6 / 최소 4 문항.
- 서답/서술형은 한 페이지 2문항(1단에 1개).
- 문제는 **항상 짝수 페이지로 마무리**(4쪽 or 6쪽). 답지는 5쪽/7쪽부터.
- MC→서술형 전환: 예) 1~15 객관식, 16~ 서술형 → 폼 16·17 슬롯 삭제, 18→16 으로 당겨 서술형1 시작.
- 서술형 마지막 뒤 남은 미주 전부 삭제해 끝번호 정합.

## 단계 (phasing) — 사용자 합의
1. **[현재] 객관식 MVP** — 표/박스/그래프/서술형 **제외**. 객관식만:
   - 문항 수 자동 조절(복사/삭제), 문제+보기 채우기, 6/쪽, 짝수쪽 마무리.
   - 표 셀 수식이 필요한 문항은 이 단계에서 **건너뛰거나 표 부분만 비움**(다음 단계).
2. 서술형 슬롯 채우기 + MC→서술형 전환/끝 미주 삭제.
3. `<보기>/<조건>` 테두리 박스, 그래프 이미지, 소문항+배점.
4. **표 셀 수식**(확률분포표·분수) — COM 한계 회피책:
   - 후보 A: 저장 후 hwpx XML 직접 패치로 표 셀에 수식 객체 주입(보기탭 주입과 동일 패턴).
   - 후보 B: 표를 텍스트(LaTeX 유지)로 우선 채우고 후속 변환.
   - 계획만 수립, 표 제외 경로 완성 후 착수.
5. [중단원/난이도] 태그 — 보류(지금 구현 안 함).

## MVP 설계 (`core/hwp_form_writer.py` 신규)
- 진입점: `write_exam_to_form(document, form_path, output_path)`.
- 흐름:
  1. 문서에서 객관식 문항 목록 추출(MVP: 표 포함 문항은 표블록 스킵 처리).
  2. 목표 객관식 슬롯 수 N 결정 + 페이지 규칙에 맞춘 패딩(짝수쪽 마무리).
  3. 폼 열기 → 서술형 슬롯(18~25) 및 잉여 객관식 슬롯 삭제 / 부족분 복사.
  4. 미주 앵커 재수집 → 슬롯별로 문제 본문(텍스트+수식) + 보기 채우기.
     - 보기 숫자=수식객체 유지(force_equation), 폼 탭 2열 정렬 재사용.
  5. 짝수 페이지 마무리 보정(말미 페이지나눔/슬롯 패딩).
  6. `SaveAs hwpx`(또는 hwp).
- 재사용: `latex_to_hwpeq`, 기존 수식 idiom([[hwp-equation-finalize]]).
- 기존 `write_exam_to_hwp`(free-flow)는 유지(폼 미사용 경로).

## 리스크
- 페이지네이션 정밀 제어(자연 흐름 + 내용 높이 가변) — MVP는 자연 흐름 + 짝수쪽 보정으로 시작, 정밀화는 후속.
- 표 셀 수식 COM 불가 — 단계4 별도 해결.
- 슬롯 복사/삭제 후 앵커 재수집 필요(인덱스 시프트).

### XML 레이아웃 엔진 성공 (2026-06-02, D:\tmp\xml_layout3.py)
- HWPX 인코딩: 단나누기=다음 `<hp:p>`에 `columnBreak="1"`, 쪽나누기=`pageBreak="1"`.
- **결정적 안전 규칙(중요)**: 섹션 XML을 `findall+join`으로 재조립하면 **단락 사이의
  비-단락 요소(구역/단 정의 등)가 누락**돼 HWP가 백지 렌더됨. → **위치기반 편집만**
  사용(속성 플립 + 정확 위치 삽입/삭제). 비-단락 요소 보존됨.
- 빈단락 삽입은 **문서의 진짜 빈단락 substring 복사**(fabricate 금지 — 파서 깨짐).
  빈단락 후보 = `<hp:t>`에 비공백 텍스트 없는 단락 중 최단(len~301).
- 엔진 흐름: 채움본 → 슬롯 opens(autoNum 위치, 헤더 이후) → 슬롯별 content/후행빈줄 분리
  → 줄수 그리디로 단 묶음(최대 3, CAP=40줄) → 아래→위로 후행빈줄 삭제 + 분배빈줄 삽입
  (even: alloc-est_lines / fixed: 3) + 단첫슬롯 columnBreak 플립.
- 결과: even 모드가 사용자 목표(균등 1/3)와 일치. 무크래시.
- 남은 튜닝: 줄수 추정(CHARS≈26) 오차로 단 마지막 문항이 다음 페이지로 밀릴 수 있음.

### 결정적 한계 발견 (2026-06-02): columnBreak는 번호단락에서 무시됨
- **테스트(test_cb.py)**: Q2 번호(autoNum)단락에 `columnBreak="1"` set → Q2가 그대로
  좌단에 남음. **HWP는 autoNum/미주 번호단락의 columnBreak을 honored 안 함.**
  (이전에 "단나누기 작동"으로 보인 건 전부 폼 자연여백에 의한 fill 흐름이었음.)
- COM `Run("BreakColumn")`은 일반 텍스트 단락엔 작동(break_test 확인)하나, fill+다수
  break+force_layout 조합은 불안정(hang/crash).
- 자연 fill(빈줄로 칸 채워 넘김)은 작동하나 줄수 추정 부정확으로 단당 문항수 드리프트
  (3 의도→4/3 갈림).
- **정확한 단 제어 방안(택1, 다음 작업)**:
  (A) 번호+문제를 **한 단락으로 병합**(fill 시 같은 para에 삽입 또는 XML 병합) →
      그 단락은 텍스트 단락이라 columnBreak honored → 정확 제어 가능. [유력]
  (B) tight 빌드 후 KeyIndicator로 **실제 줄높이 측정** → 정확 빈줄 산정.
- 사용자 요구(스샷): 단 안 균등(Q4-Q5 줄이고 Q5-Q6 띄움), Q7 단 맨위 시작.

### 돌파구 (2026-06-02): columnBreak는 **바깥 endNote 단락**에 걸어야 함
- 수기 완성본(194차) XML 분석 결과: 단나누기 columnBreak 7개 사용, pageBreak 0,
  빈 단락 53%로 간격. columnBreak는 `<hp:endNote>`를 가진 **바깥 `<hp:p>`**에 걸려 있음.
- **그동안의 진짜 버그**: `<hp:endNote>`는 `<hp:subList>` 안에 **중첩 `<hp:p>`**(미주 내용)를
  가짐. 내 정규식 `<hp:p\b.*?</hp:p>`가 **안쪽 단락**을 잡아, columnBreak를 미주 내용
  단락에 걸고 있었음 → 본문 흐름에 무효. (그래서 "columnBreak 무시됨"으로 오판)
- **해결 검증(tcb3, xv4)**: `<hp:endNote>` 위치 → `rfind("<hp:p ")`로 **바깥 단락** 찾아
  columnBreak="1" → 실제로 단나누기 작동(Q2가 우단으로 점프, xv4가 정확히 3/3/1).
- 파싱 시 endNote/표/equation을 **마스킹**해야 바깥 단락만 잡힘(중첩 안전).
- 남은 일: 폼 과잉 빈줄 제거(안 하면 Q4-6 빈줄이 다음 단까지 넘쳐 Q7이 밀림) +
  단 안 균등 빈줄. → 마스킹 후 위치기반 편집(삭제/삽입)+언마스킹(xml_v5.py, 슬롯검출
  인덱싱 버그 수정 필요). columnBreak 메커니즘 자체는 해결됨.
